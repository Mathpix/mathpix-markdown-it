# PR: List rendering robustness fixes

Status: Implemented
Owner: @OlgaRedozubova
Base: master
Version: 3.1.0

---

## Context

Several unrelated inputs made LaTeX `itemize`/`enumerate` lists render incorrectly. The fixes live in the list-env, tabular, and footnote block rules, plus the marker-padding CSS, and ship together.

## Fixes

1. **Marker padding for block-content items.** A top-level list gets its `padding-inline-start` from the widest custom `\item[...]` marker, but the marker width was only measured on the inline item path. Items whose content is a block environment (`\begin{figure}`, `\begin{tabular}`, a code fence) were skipped, so a list whose long-marker items all held block content lost its padding. The width calc is now shared and applied on the block item path too.

2. **Marker width: fullwidth/CJK, math, and wrapped content.** Marker width summed `String.length` over top-level `text` tokens only, so several markers were undercounted (too small an indent): fullwidth/CJK (`\item[11．]`, U+FF0E) counted as narrow ASCII — now East-Asian Wide/Fullwidth chars are measured as wide glyphs; math (`\item[$x^4+x^4$]`) contributed 0 — now uses the token's rendered `widthEx` (the same field `getTextWidthByTokens` reads); wrapped content (`\item[\textbf{…}]`) contributed 0 — now measured by recursing into the wrapper's children. The width helpers live in `common/display-width.ts` (`textReserveEm`, `tokenMarkerWidth`); `computeMarkerPadding` (list module) delegates to them. See fix 5 for the em model.

3. **No state leak from a speculative list parse.** The list block rule parses the body into a buffered state before deciding whether to commit; on a silent probe (now run as a footnote/paragraph terminator) or an abort, the tokens are discarded. Three leaks from that discarded parse are closed. The first two caused empty `<>` item bodies (a leaked `env.isBlock=true` wakes the inline list fallback on later content); the third shifted caption numbers:

   - **Speculative parse.** The list block rule parses into a buffered state that shares `env` by prototype, so it mutates the real `env` (`isBlock`, `inheritedListType`, `parentType`, `prentLevel`). It now snapshots those four transient **env** keys on entry and restores them in a `finally` on every exit — abort, silent probe, commit, or exception — so a silent probe never changes `env` and an unclosed `itemize` before a `tabular` degrades to plain text exactly as without the `tabular`. (The module-global list depth is a separate, pre-existing concern — see Non-Goals.)
   - **`envToInline` snapshot replay.** A `tabular` inside a list item snapshots the whole `env` into `token.envToInline` while `isBlock=true`; `core-inline` later `Object.assign`s that snapshot back onto the shared `env`, re-leaking `isBlock` **after** the block-rule `finally` and, within the same token loop, waking the fallback on a following list. The snapshot now strips the transient list flags (`snapshotEnvForInline`, single source of truth `LIST_TRANSIENT_ENV_KEYS` in `common/env-transient.ts`); the block item path also resets `isBlock` after block content. Covered by tests over figure/tabular × closed/unclosed × order.
   - **Nested-rule env.** The nested block rules write onto the shared `env` while the body is parsed: the float rules (`begin-table.ts`) write `caption`, `captionPos`, `captionIsLabelFormatEmpty`, `captionIsSingleLineCheck`, `envType`, `align`, `alignEnvBlock`, `number`, `type` — where `StatePushCaptionTable` later consumes the caption keys, so an unconsumed `\caption` from a discarded parse could surface on an unrelated float — and `begin-tabular` writes `isInline`, `subTabular`, `tabulare`. `LIST_SPECULATIVE_ENV_KEYS` covers all of them; they are snapshotted and restored on a non-committing exit only, on commit the flushed tokens own them. The same keys are written by rules other than the floats (`number`/`type` also by section numbering in `mdPluginText.ts`, `align` by `begin-align.ts`, `isInline`/`subTabular` by `md-block-rule/helper.ts`, `tabulare` by `md-inline-rule/tabular.ts`), so the set is a hand-maintained list, not one derived from its write sites. Drift is caught behaviourally rather than statically: the probe cases in `tests/_parse-isolation.js` compare a full key+value `env` snapshot across list bodies holding a figure, table, align, section, label, footnote, tabular, fence and display math, so a rule that starts writing a new key inside a list body fails a test. The inline path needs no equivalent: `buildBlockStateFromRaw` gives it a **copy** of `env`. No render defect was reproduced from this key set — it is closed by audit, alongside the counters below, and pinned by the float/tabular probe cases in `tests/_parse-isolation.js` (a full key+value `env` snapshot). Note the rollback covers only a *discarded* parse: `begin-table.ts` never clears the float keys itself, so after a **committed** float they persist (`env.align` is then read by `includegraphics` under `centerImages`) — reproducible with no list involved, pre-existing, out of scope here.
   - **Caption counters.** The speculative parse runs the body's `\begin{figure}` / `\begin{table}\caption`, which bumps the module-global figure/table counters (extracted to the leaf module `common/caption-counters.ts`; `begin-table.ts` only increments them). On a non-committing exit the tokens are discarded, so the counters are snapshotted and restored too (`getCaptionCounters`/`setCaptionCounters`, restored unless the parse committed) — in the `Lists` block rule's `finally` and inside `parseListEnvRawToTokens` for the inline path. This fixes `\footnote` after such a list shifting `Figure N` / `Table N` by one, **and** the pre-existing inflation from the paragraph-terminator probe (a figure-in-a-list is now `Figure 1`, was `Figure 3`).

4. **Footnote block rules stop at a list start.** The `\footnote`/`\footnotetext` block rules scan forward for their open tag, terminating at block boundaries so the scan doesn't swallow following blocks. The LaTeX list rule (`Lists`) was not among the terminators, so a `\begin{itemize}` between a paragraph and a later footnote (no blank line) did not stop the scan: the list was swallowed and rendered as literal text (a blank line masked it).

   - `latex_footnotetext_block` already ran the full terminator set; adding `Lists` to that set fixes it.
   - `latex_footnote_block` terminated on `fence` only (a deliberate cost choice — see `2026-05-footnote-perf-and-parser-invariants.md`); it now also runs `Lists`. Kept minimal (`fence` + `Lists`, not the full ~20-rule set). The `Lists` silent probe fast-bails on non-`\` lines; on an actual `\begin{list}` line it runs a full speculative parse, but that line ends the scan anyway.
   - Performance: a **fix**, not a cost. On repeated paragraph + list-with-footnotetext units without blank separators, the missing list terminator made the footnotetext scan run across every `\begin{itemize}` into the rest of the document — O(N²) (seconds on large inputs). Terminating at the list bounds each scan to one unit → linear; guarded by a scaling test in `tests/_footnotes_latex.js`.
   - The probe answer is memoized per state (`LIST_PROBE_KEY`, invalidated when `state.src` is reassigned), because a silent `Lists` probe still runs the whole speculative parse — it must, since the rule is strict and an unclosed env has to answer `false`. Terminator scans re-ask for the same line at every block start, so without the memo those parses dominate. Key: `startLine`, `endLine`, the first line's geometry (`bMarks[startLine] + tShift[startLine]` and `eMarks[startLine]`) — a blockquote shifts those for the same line numbers on one state, so line numbers alone don't pin the content — and the state fields `ListOpen` reads (`parentType`, `prentLevel`, `env.inheritedListType`). `blkIndent` is deliberately **not** in it: the rule never reads it, pinned by an omitted-field case in `tests/_parse-isolation.js` (a cached answer must equal an unmemoized one under the same mutation), alongside `sCount`, `state.types`, `state.level` and the `env.isBlock`/`parentType`/`prentLevel` trio. The keyed half is pinned by the opposite case: two list starts on one state keep separate answers. Later lines' `eMarks` are outside the key — the only in-place writers are `begin-align.ts` (two sites), and neither fires for any align-inside-a-list shape tested; output is byte-identical with the memo disabled on five such shapes. Measured with and without the memo on two shapes: 200 repetitions of `paragraph + \begin{itemize}\item[] \footnotetext{…}\end{itemize}` with no blank separators — **34.4 → 20.4 ms**; and 20 blank-line-separated lists of 100 `\item[N.]` entries with a trailing `\footnote` — 29.2 → 29.6 ms, i.e. no effect, because a blank line already ends each scan. So the memo pays off exactly where a terminator scan re-probes the same line, and costs nothing elsewhere. Output is byte-identical with and without it on both shapes and across the fixture corpus.
   - `Lists` also gets a fast bail (first-char check before allocating a substring), since it now runs as a per-line terminator in paragraph/footnote scans.
   - **Closer lookahead: an unclosed env answers `false` without parsing.** The strict rule can only reject an env with no `\end`, but it used to discover that by parsing the body to EOF — once per probe, and terminator scans probe every line, so a document of unclosed `\begin{itemize}` starts was quadratic. Two paths carried it, both now check for a closer first and bail: the block rule caches the last `\end{itemize|enumerate}` offset per state (`lastListEndPos`, invalidated on `state.src` reassignment — one sweep per document, verified by counting: 16 KB scanned for a 16 KB source), and `findFirstCompleteListEnv` searches from `startPos` before its char-by-char walk, which slices the remainder and runs two unanchored regexes at every position (44% + 34% of profile self time before the fix). Both lookaheads are exact, not heuristic: the sweep regexes are built from `END_LIST_ENV_INLINE_RE.source` — the same pattern the parser accepts — and each function has a single success path that requires a closer, so "no closer ahead" cannot change any answer. Measured on `\begin{itemize}\n\item[a] x` repeated (parse only), base → HEAD: n=100 197→6 ms, n=200 892→10 ms, n=400 4876→11 ms — quadratic to flat. Cost where the bail does not fire is below noise (closed lists ×400, one list + 400 KB of text, nested lists, lists-in-tabular: all within run-to-run spread over 15 iterations), and memory is one `{src, lastPos}` object per state (8 KB heap delta over 20 renders of a 400-list document). Pinned by a scaling case in `tests/_footnotes_latex.js`; with both lookaheads removed it fails and the file takes 3 min instead of 5 s.
   - **Residual ceiling, pre-existing and not list-related.** With all three lookaheads in place, an unclosed env repeated with **no blank line anywhere** is still super-linear: 193 ms at n=400 for the list form, 304 ms for the tabular form. `\footnote` is *not* part of it — the same shapes without any footnote measure 15/51/193 ms and 20/78/304 ms, i.e. within noise of the footnote versions. What remains is two rules that scan forward from every block start and never terminate on this input: `newTheoremBlock` (401 calls, 688 ms at n=400) and markdown-it's core `lheading` (401 calls, 395 ms); their cost is almost entirely nested, since every line of those scans probes ~20 terminator rules, which is why a CPU profile of the shape looks flat rather than pointing at either rule. Every terminator that used to be expensive is now cheap (`Lists` 484 397 calls / 47 ms, `BeginTabular` 724 999 / 44 ms), so the residual is the sheer probe count, not any one rule. Skipping the `newTheoremBlock` scan the same way was implemented and reverted: the rule can only match one of four literals, so the bail is sound on paper, but its scan is load-bearing — it leaves `state.parentType = 'paragraph'` on every failure path (restored only on success), and its terminator probes mutate global state of their own, so four list-in-tabular fixtures change. That coupling, and `lheading` being core, is why the ceiling stays. An unclosed `theorem`, `align` or `lstlisting` is linear (30/10/28 ms at n=400), and a blank line between units removes the cost entirely (10 ms at n=400).

5. **Marker padding emitted in `em`, not `px`, so it scales with the container font.** `px` padding does not track a consumer-set container `font-size`, and the previous `ex→px` conversion undercounted math: a `7.329ex` math marker got `51px` reserved while it renders ~68px, so the marker was clipped. Marker widths are now measured in em:
   - **Math** uses its exact rendered `widthEx` converted to em (`EX_TO_EM = exDef/fonSizeDef ≈ 0.5186`), so `$x^4+x^4$` reserves `7.329ex → ~3.80em` + `0.625em` gap ≈ `4.43em`. `widthEx` exists only for SVG output; under `skipMathToHtml` / non-SVG output there is no measured width, so the marker keeps the default indent rather than a fabricated estimate.
   - **Text** (and code-span / wrapper content) uses a per-glyph-class estimate (`textReserveEm`): narrow (`. i l space ( )`) `0.40em`, normal `0.62em`, wide (most capitals, `m`) `0.90em`, extra-wide (`W @ %`) `1.10em`, East-Asian Wide `1.20em` — over the BMP ranges **and** the astral Wide blocks (emoji and Enclosed Ideographic Supplement U+1F200–1FAFF, CJK Ext-B–G U+20000–3FFFD, Ideographic Symbols/Tangut incl. Supplement/Khitan U+16FE0–18D08, Kana Extended-B through Nushu U+1AFF0–1B2FF), so an emoji marker reserves the same as an ideograph (`\item[😀😀]` → `3.03em`, identical to `\item[一一]`; it used to fall through to the cased branch at `0.90em`, land at `2.425em` and emit no attribute at all) — zero-advance code points `0` (combining marks U+0300–036F, U+1AB0–1AFF, U+20D0–20F0, U+FE20–FE2F, U+3099/309A, which render over the base glyph; plus the joiners and selectors that compose their neighbours instead of taking a cell — U+200B–200F and the variation selectors U+FE00–FE0F, kept as a separate range from the half marks because Vertical Forms U+FE10–FE19 sit between them and are Wide, without which an emoji ZWJ sequence reserved a full glyph per joiner: `👨‍👩‍👧` went from `5.40em` to `3.60em`, and `❤️` from `1.80em` to `0.90em`), and every other non-ASCII char by case: uppercase `1.10em`, the rest `0.90em` (a lone surrogate is broken input and reserves 0). The blocks are approximated whole, so the few Neutral code points inside them (Ornamental Dingbats, say) over-reserve — the safe direction, and the same trade-off the rest of the model makes. Code spans and `\texttt{…}` render as `<code>` in a monospace face where those classes underreserve (`` `iiiiiiiiii` `` needs `5.63em`, the narrow class gave `4.63em`), so they are measured at a flat `0.62em` per character — above the widest face `code` uses (DM Mono `0.6em`, Inconsolata `0.5em`). These are generous margins over Helvetica advances (≈1.07× for the widest glyphs up to ≈1.8× for the thinnest like `i`/`J` on all-same runs), not exact — the *shape* (narrow < normal < wide) holds for any proportional font. Wrapped (`\textbf{…}`) and code-span markers recurse/measure their content; `html_inline` markup is not measured (0).
   - Both text and math widths get **one** `0.625em` marker→content gap (`.li_level { padding-right }`, was `10px`). The default list indent is `2.5em` (`LIST_DEFAULT_INDENT_EM`, was `40px`).
   - A custom marker overrides the default only when it **overflows** the available indent — for a flat list that is `> 2.5em`; nested lists also count the ancestor indent (see Non-Goals) — so the padding never resolves below the default, and is clamped at `LIST_MAX_INDENT_EM = 20em`.
   - `data-padding-inline-start` now holds the em value **with its unit** (e.g. `"4.43em"`, was a bare px number) so the value is self-describing.
   - vs 3.0.1: measured against real font metrics (the bundled Arial fixture, `tests/_data/_markdownToHTMLWithSize/fonts/Arial.ttf`), 3.0.1's flat `14px`/char over-reserved narrow/digit markers by 36–70% and under-reserved all-caps by ~14%; the class estimate holds a +11…+30% margin — tighter (correct) for narrow/normal, wider (safer) for all-caps. Math unchanged.

6. **`\item` detection requires a real `\item` command.** The item-command regexes matched too loosely: `LATEX_ITEM_COMMAND_INLINE_RE` matched the bare word `item` (no backslash), and `LATEX_ITEM_COMMAND_RE` / `LATEX_LIST_BOUNDARY_INLINE_RE` matched any `\item`-prefixed command (`\itemsep`, `\itemindent`). So a list-item body containing such text was split into a spurious extra item, and a multiline `\footnote` / `\footnotetext` inside an item was broken mid-brace and rendered as literal text (`\footnotetext{…item…}` shown verbatim). All three now require a real command: the `\item[...]` bracket form, or bare `\item` with a command boundary (`\\item(?![a-zA-Z])`). `ItemsListPush` split a line on a plain `indexOf('\item')` and needed the same anchoring (`LATEX_ITEM_SPLIT_RE`): `tail \itemsep pad \item[b] y` split at `\itemsep`, so `tail` lost its trailing space and the rest was mis-attributed. The command itself still reaches the output as literal text — that is what this library does with any unrecognised LaTeX command (`\raggedright`, `\vspace`, `\hrule` behave the same), so it is left alone here; note that such text placed before the first `\item` lands as a bare text node inside `<ul>`, which is invalid HTML — a pre-existing, command-agnostic issue, out of scope here. Pre-existing (the regexes predate this PR — introduced with the tabular-in-itemize fix); the item family is the only regex class with this issue (the `\begin{…}`/`\end{…}` env regexes require braces, and the footnote token guards already carry `(?![a-zA-Z])`).

7. **Markdown lists indent in `em`, not the browser default.** Core-markdown `<ul>`/`<ol>` (no `.itemize`/`.enumerate` class) had no `padding-inline-start`, so browsers used their `40px` default — which doesn't scale when a consumer sizes content via `font-size`. A rule now sets `padding-inline-start: 2.5em` (`LIST_DEFAULT_INDENT_EM`, `styles-lists.ts`), matching the LaTeX-list default and scaling with the container. Per `2026-03-mmd-css-scoping.md`, `ul`/`ol` are generic HTML elements, so the rule is **scoped only** (`#preview-content ul, #setText ul, #preview-content ol, #setText ol`) — a bare `ul { }` would restyle the host page. LaTeX lists are unaffected (their `.itemize`/`.enumerate` class rules and inline custom padding win by specificity, same `2.5em`). It also covers the generated footnotes list (`<ol class="footnotes-list">`), which had no explicit padding — same `2.5em`. TOC lists are held at `padding-inline-start: 0` by a guard in the same (always-emitted) `lists` module — `#preview-content #toc_container ul, #setText #toc_container ul` (and `ol`), specificity `(2,0,1)`, which beats this rule `(1,0,1)` **independent of bundle order**. This is deliberate: `TocStyle`'s own `#toc_container ul { padding: 0 }` is only emitted when `toc` is enabled, so relying on it (or on the `lists`-before-`toc` order) would leave a consumer that renders a visible `#toc_container` inside `#setText`/`#preview-content` without `TocStyle` with a `2.5em` TOC indent. The guard matches any `ul`/`ol` inside a wrapper-nested `#toc_container` — not only the TOC's own list — so at `(2,0,1)` it also outranks the scoped `.itemize`/`.enumerate` rule (`#preview-content ul.itemize`, `(1,1,1)`) by id count: a LaTeX list nested inside such a `#toc_container` would be zeroed too. Purely theoretical (TOC content is generated), accepted over a `:not(.itemize)` carve-out. The in-content TOC (`.table-of-contents`, emitted `display:none`) is held at `0` by the same guard: it would otherwise pick up the `2.5em` if a consumer revealed the block, and at `(1,1,1)` it outranks the scoped generic rule `(1,0,1)`. Unlike the `#toc_container` half, this one is **not** order-independent — it ties with `#preview-content ul.itemize` `(1,1,1)` and wins only by coming later in the same stylesheet, so a LaTeX list nested inside a revealed `.table-of-contents` would follow load order. Theoretical (TOC content is generated), and the same trade-off as the `#toc_container` guard. Otherwise a TOC in the normal separate `#toc_container` is unaffected.

8. **Item body of a single-line nested list survives the table-cell export.** A list written fully on one line unwraps its item body to bare inline tokens pushed straight into the cell stream (not an `inline` wrapper), and `renderNonTableTokenIntoCell` only rendered such leaf tokens to HTML — their `table-markdown` / `tsv` / `csv` / smoothed text was dropped, so `\item[x] d` in a cell exported as `x ` without the `d`. The leaf branch now also collects them through `renderTableCellContent`. It is fed the **whole consecutive run** of leaf tokens in one call, not one token at a time, because that function consumes siblings — a link is `link_open` + `text` + `link_close`, so a per-token call loses the href (`[t](http://a.b)` → `t`, tsv `http://a.bt`). List-structural tokens are excluded (`LIST_STITCH_TOKEN_TYPES`); their Markdown comes from `handleListTokensForCellMarkdown`. HTML output is unchanged, and cells whose content is a normal `inline` token are untouched. Scope: `isLeafRunMember` is structural, not list-specific — it matches **any** unwrapped inline token in a cell that carries no children of its own, so a link, bold/italic, code span or inline math sitting directly in a cell now reaches the export as well. An `image` is *not* a run member (`!token.children?.length` excludes it — its alt text lives in `children`); it is handled by the pre-existing `token.children?.length` branch above and splits a surrounding run into two, which the export joins back. Narrowing the predicate to a fixed type list was rejected on behaviour, not on an inventory of observed types: text, links, bold, italic, code spans and inline math all export correctly through the structural predicate, and an allow-list would have to name each one or silently drop it. A run cannot cross a cell: `td_open`/`td_close` are in `TABLE_TOKENS`, which ends it — pinned by two-cell fixtures in `_table-markdown` and `_tsv`.

   - **The smoothed accumulator picks the same source in both loops.** The link loop appended the rendered HTML of each consumed token, while the main loop prefers the token's own `tableSmoothed` lines and only falls back to the rendered form — two places building one accumulator by different rules. `tableSmoothed` is assigned in exactly one place (`render-tabular.ts`, on a token rendered as a table), so the divergence needs a table inside the label: `[\begin{tabular}{l}q\end{tabular}](url)` in a cell under `forPptx` put `<a …><div class="inline-tabular"><table …>` into the smoothed stream, where the same table outside a link gives `q`. Inline math does **not** diverge — it carries no `tableSmoothed`, so both loops fall back to the rendered form (its smoothed shape being the SVG is by design, not this bug). Both call sites now go through one `smoothedFor` helper; pinned in `tests/_tabular.js`.
   - **The leaf run no longer claims to be a sub-table.** `renderTableCellContent` stamps `isSubTable` onto every token it walks, and later passes read it back off them (the `sub-table` class, `convert-math-to-html`'s options, and the ascii serializer, which uses it to suppress tsv/csv/md). The leaf-run call passed a hard-coded `true`; it now passes the enclosing table's nesting, which is `false` in all 44 firings across the fixture corpus. No output change: rendering five leaf-run shapes (text, link, bold, image, math in a one-line list inside a cell) under both variants gives identical HTML **and** an identical set of stamped tokens, because every token the leaf run touches is stamped anyway by the pre-existing recursion for `inline` children — which is why the invariant "no cell token carries `isSubTable`" does not hold on this branch or on the base commit. That recursion also hard-codes `true`; propagating the real nesting there passes the whole suite too, but is left alone deliberately — no fixture covers a `tabular` inside math inside a cell, the one shape where the ascii serializer's gate would flip, so a green run is not evidence there. The mutation contract itself is pinned in `tests/_tabular.js`: the stamp follows the argument, and a `tabular_inline` child marks itself whatever the caller passes.
   - **Link label composition (`getMdLink`).** The Markdown writer read only the token right after `link_open`, which emptied a formatted label (`[**b** x](url)` → `[](url)`); it now walks to the matching `link_close` with depth tracking. Per inner token: a `text` node contributes its content with `]` re-escaped (markdown-it hands it over unescaped, and an unescaped `]` closes the label early), a `code_inline` contributes marker + content + marker, a `smiles_inline` marker + content + `</smiles>` (its closer is not in `markup`), and anything else contributes its `getMdForChild` marker **or, when that is empty, its `content`** — which is what keeps an image label at its alt text and an inline-math label at its LaTeX source, the shapes the single-token read happened to cover. The fallback is not re-escaped: an image keeps the raw source in `content` (already escaped), and escaping the math branch would corrupt the LaTeX, so a `]` inside a math label still breaks it — unchanged from before, and the same trade-off as the href-only `tsv`/`csv` output. Why those two types are enumerated rather than detected: `getMdForChild` is the only source of markers, so a type outside its switch gets `'' || content` and cannot lose content; of the types inside it, all but `code_inline` and `smiles_inline` are `_open`/`_close` pairs that carry none. Checked empirically too — 19 inline constructs (bold, italic, code, `\texttt`, math, display math, image, smiles, strike, mark, `\underline`, `\textbf`, `\textit`, `html_inline`, sub, sup, `\textcolor`, `\icon`, autolink) exported as a label and bare in the same cell: no remaining content loss. Three known **form** differences stay: an image label degrades to its alt text and a math label to its LaTeX without delimiters (both the pre-PR shape), and an autolink label keeps its text but not its href — a nested link has no Markdown form. Fixtures cover the formatted, image, math, smiles and escaped-`]` labels; there is no `texttt` token type in the stream (`\texttt{…}` arrives as `texttt_open`/`text`/`texttt_close`), so the writer does not test for one.

9. **An unclosed `\begin{tabular}` no longer costs a scan to EOF per probe.** Same defect as the list lookahead in fix 4, in a different rule and with a much higher ceiling. `BeginTabular` scans forward from the start line and only afterwards checks `if (!isCloseTagExist) return false`, so an env with no `\end{tabular}` is rejected only after reading the rest of the document. Terminator scans re-ask the rule at every line, so a document of unclosed `\begin{tabular}` starts with no blank line anywhere was quadratic: **160 ms at n=100, 1239 ms at n=200, 9422 ms at n=400** — 30–45× the list shape (205 ms at n=400), and reachable with no list in the input at all. The rule now consults a per-state offset of the last closer (one sweep per document, invalidated when `state.src` is reassigned) and bails before the scan: **9422 → 309 ms at n=400**; `BeginTabular` itself drops from 6422 ms over 724 999 calls (~9 µs each) to 44 ms (~0.06 µs). The bail is exact rather than heuristic: the sweep regex is built from this module's own `closeTag`, the pattern `findOpenCloseTags` accepts, and the rule's only success path lies past the `isCloseTagExist` check, which is set only by a closer found at or after the start line. Not list-related — included here because it is the same probe-per-line pattern, reached by the same malformed-LaTeX documents that motivated fix 4, and it dominated every measurement of that work.

## Migration

- **`data-padding-inline-start` changed from a px number to an em value with unit** (`"56"` → `"4.23em"` on the `tests/_data/_footnotes/_html.js` fixture). A downstream consumer that reads this attribute as px must update to parse the em value; the only in-repo reader (the list renderer) is updated.
- **Custom-marker `padding-inline-start` and the default list indent (`2.5em`) are now em; the marker gap is `0.625em`** (all were px). Layout is ≈ equivalent at a 16px base but now scales with the container `font-size`.
- **A custom marker's rendered HTML no longer carries edge whitespace.** `markerTokens` are now parsed from the trimmed marker (so the width is measured as it renders), which also changes the emitted marker: `\item[   wide   ]` was `<span class="li_level">   wide   </span>`, now `<span class="li_level">wide</span>`. `token.marker` was already trimmed before this PR; only the parsed tokens (and hence the HTML) changed.
- **`data-padding-inline-start` is now emitted on nested lists too**, not only the outermost list token. A `forDocx` / downstream consumer that assumed only the top-level list carries it will now see it on inner lists.
- **An inline-opened `*_list_open` token now carries `prentLevel` = its nesting depth** (e.g. `1` for a once-nested list), matching the block path; before, an inline-opened list-open token kept the pre-increment value (`0`). `render-tabular`'s cell stitching reads this field, so a single-line nested list in a table cell now gets the same `<br>` before the sublist as the own-line form — `table-markdown` output for that cell changes from `| 1. a&#160;&#160;x <br> |` to `| 1. a<br>&#160;&#160;x d<br> |`. Two independent effects are folded into that one diff: the `<br>` after `a` is this `prentLevel` change, and the item body `d` is fix 8; the trailing `<br>` pre-dates this PR. A downstream consumer reading `token.prentLevel` off a list-open token is affected too.
- **The speculative-parse env rollback sets restored-but-previously-absent keys to `undefined` instead of deleting them.** `delete` transitions the shared `env` to dictionary mode for the remainder of the parse, which slows every later `env` read — measured ~12% on list-heavy input and ~21% on lists holding a float (the rollback fires on every silent probe). All readers of these keys test the value, so behaviour is unchanged; but a consumer that passes its own `env` object and inspects it after the parse now sees the keys present with value `undefined` (`'isBlock' in env` → `true`, `Object.keys(env)` includes them). The isolation tests assert the value-level invariant accordingly. Closed for the keys where it matters: `snapshotEnvForInline` drops `undefined`-valued keys of `LIST_SPECULATIVE_ENV_KEYS` so a rollback cannot clear a value that goes live later (reproduced: `env.align` ended `undefined` instead of `"center"` when a list-with-tabular preceded a `\begin{center}` block; pinned in `tests/_parse-isolation.js`). The `begin-tabular` trio (`isInline`, `subTabular`, `tabulare`) is exempt — it sets those `undefined` on purpose (`outMath.include_tsv` when unset) and the tsv/csv export depends on that reaching the replay; filtering them breaks 12 export tests.
- **The caption-counter helpers moved module and changed case: `ClearTableNumbers`/`ClearFigureNumbers` → `clearTableNumbers`/`clearFigureNumbers`.** They were exported from `lib/markdown/md-block-rule/begin-table` and now live in `lib/markdown/common/caption-counters` (extracted so the counters have a leaf module the list rule can snapshot without importing the float rules). A deep import of the old path loses both names — no re-export was left behind, so the call fails at import time under TS and at call time in JS. The public entry never exported them, so only deep imports are affected, and there is no public-entry substitute: `resetMmdGlobalState()` does not touch these counters (they are cleared when `mdPluginTableTabular` initialises). Consumers that called them to stop `Figure N`/`Table N` drifting between documents may not need them at all now — a discarded speculative parse no longer bumps the counters (fix 3).
- **Deep-import types changed** (`lib/markdown/md-latex-lists-env/latex-list-types`): `ListItemsResult` and `ListInlineContext` dropped `padding` and gained required `openTokens`/`allListTokens`. A TS consumer deep-importing these (not via the public entry) must update; runtime output is unchanged.
- **Markdown-list indent is now `2.5em`, not the browser default `40px`** (identical at a 16px base, but now scales with `font-size`). The rule matches **any** `ul`/`ol` inside the wrapper (`#preview-content`/`#setText`) — including a consumer's own HTML lists under `htmlTags: true` — not only markdown-generated ones. Applies to wrapped output only; raw `markdownToHTML()` without a wrapper keeps the browser default. It also covers the numbered footnotes list (`<ol class="footnotes-list">` → `2.5em`); the no-numbers footnotes list keeps its inline `padding-left: 20px` (`render-rule.ts`), which wins by cascade — so numbered vs no-numbers footnote lists differ (`2.5em` vs `20px`), a difference that pre-dates this PR (it was `40px` vs `20px`) but is now pinned by the rule.
- **The wrapped-list padding floor rises from the UA default (specificity 0) to `(1,0,1)`** (`#preview-content ul`/`#setText ul`). A consumer rule at class specificity — e.g. `.my-list { padding-inline-start: 1em }` (0,1,0) — that previously beat the UA default will no longer override the list indent; it must match or exceed `(1,0,1)` (or load after MMD styles at equal specificity).

- **Content before the first `\item` sits directly inside `<ul>`, which is invalid HTML — consumers that walk the DOM are affected.** Anything on a line before the first `\item` reaches the output as literal text where it stands: an unsupported command (`\itemsep 1pt`, `\raggedright`, `\vspace{1pt}`, `\hrule`), plain text, a code span, even a `\begin{tabular}`. In HTML that lands as a text or element node between `<ul>` and its first `<li>`, so `forDocx`, sanitisers and table extraction may drop or relocate it. Pre-existing and command-agnostic — this PR only makes it more visible for the `\item`-prefixed commands, which used to be mis-parsed as `\item` and swallowed into an `<li>` (`\itemsep 1pt` rendered as a bullet item reading `sep 1pt`). Not changed here, deliberately: the input is **malformed LaTeX** (real LaTeX raises *"Something's wrong--perhaps a missing `\item`"* and typesets nothing), and unsupported commands reaching the output as text is the library's convention for every such command, not something specific to lists. Wrapping the content in a marker-less `<li>` was implemented and measured: it produces valid HTML and keeps the text, but changes six fixtures, moves a pre-item `<table>` inside an `<li>`, and gives a no-output LaTeX command its own list row — a worse presentation for the one input in this set that is legal LaTeX. Pinned by the fixture `\item detection: \itemsep before the first item makes no item`, so any future change to the placement is visible.

## Non-Goals

- The transient env flags, the caption env keys and the caption counters are restored around the speculative parse (fix 3); the list **depth** (`list-state.ts`, `openItems`) is deliberately left alone.

  - It is a running tally of the `<li>` already emitted, not independent state, so it has to follow token emission rather than the commit decision. Rolling it back on a discarded parse desyncs it from the tokens and emits a stray `</li>` (measured: four lists-inside-tabular fixtures).
  - A discarded parse therefore leaves it advanced. Bounded and inert: the core `reset_mmd_global_state` hook clears it at the start of every full parse, so nothing crosses documents, and later lists in the same parse render identically — pinned in `tests/_parse-isolation.js`.
  - The diagnostics in `list-state.ts` report each distinct case once per parse, so a hot probe path cannot flood a consumer's log. Two knock-on effects: the memo skips the speculative parse on a cache hit, so how far the counter advances depends on hit/miss, and the de-duplicated warning makes a desync less visible than before — both deliberate, neither observable in the output.
  - `sectionCount` (`mdPluginText.ts`) is likewise not restored, but sections do not occur inside list bodies in practice. `labelsList` was checked and does not drift — pinned in `tests/_parse-isolation.js` (an `\label` inside an item body registers through the theorem inline rule and resolves to the same `\ref` number whether the list is probed or not).
  - The **theorem counters** are not restored either, and are left untested: a `\begin{theorem}` inside a list body is never rendered — it reaches the math converter as an unknown environment, and its content is dropped with a `[TexConvert] ERROR` log. Verified over six shapes (`\item` same line, after item content, blank-line separated, `itemize`/`enumerate`), and identically on the base commit `65259c1c`, so it is pre-existing and not a regression from this PR. The counter therefore cannot advance from a speculative parse, and a test over that shape would pass for an unrelated reason. It does number inside a **markdown** list (`- a` + indented env), but that path involves no speculative parse. Making theorem envs work inside a LaTeX list body is out of scope here.
- Malformed input still degrades gracefully; the goal is text, not a partial list.
- The footnote-scan terminator (fix 4) fires only on a **syntactically closed** list env (the `Lists` probe returns false for an unclosed `\begin{itemize}` in strict mode), so an unclosed list before a footnote tag is not a scan boundary. No reproduced defect: it degrades to literal text and the footnote section does not absorb it.
- Text reserve is per **glyph class**, not per exact glyph — a coarse approximation with a margin, tuned to a Helvetica-like font.

  - Classes resolve by range: ASCII through a lookup table built from the class regexes; East-Asian Wide/Fullwidth as full-width, over the BMP and astral Wide blocks alike; **everything else by case** — uppercase to extra-wide, the rest to wide — because the class regexes are ASCII-only and would otherwise put uppercase Cyrillic/Greek/accented Latin in the `normal` class and clip the marker. Astral non-Wide chars (math alphanumerics, Deseret) are caseless or cased and resolve there, not in `full-width`; the wide check runs first, so a Wide astral char never reaches the cased branch and never allocates.
  - The case test is the only step that allocates (`String.fromCodePoint` + two case foldings), so it is the only one memoised — as one byte per code point in a fixed `Uint8Array` over `0x0000–0x2FFF`, the dense range: Latin-1 through General Punctuation, arrows, math operators and symbols, ending where the Wide CJK blocks take over. The size is therefore constant (12 KB) and independent of input, which is why this cache needs no lifecycle owner, unlike the per-parse caches elsewhere in the parser — a keyed map would have grown with every distinct rare code point a document happens to contain (~860 000 non-Wide code points exist, so tens of MB in the worst case, retained for the life of the process). Above the bound the class is recomputed per occurrence: measured at ~70 ns per code point (2800 Deseret chars: 0.04 → 0.19 ms), which is irrelevant here because the only caller measures list **markers**, and no realistic marker is thousands of astral characters long.
  - Code spans and `\texttt{…}` render as `<code>` in a monospace face where those classes underreserve, so they are measured at a flat `0.62em` per cell — above the widest face `code` uses (DM Mono `0.6em`).
  - **Accepted, not covered:** 32 non-ASCII glyphs in the bundled Arial still reserve less than they render, by at most `0.198em` each — wide punctuation and symbols (`—`, `…`, `‰`, `№`, `™`, arrows, geometric shapes), Arabic forms, `œ`, `љ`. A marker built only from those clips slightly (`—————` reserves `5.13em` against `5.63em`); one such glyph among letters does not, because the letters around it over-reserve. Adding per-block extra-wide ranges was rejected as font-specific whack-a-mole that would over-reserve narrow punctuation in the same blocks (`’` would go from `0.19em` to `1.10em`).
  - The other cost is over-reserving lowercase non-ASCII by ~1.5× (`примечание` reserves `9.63em` against `6.27em`). Lowering it to the normal class was rejected on measurement: 1017 of 1239 lowercase non-ASCII glyphs in Arial (82%, including 76 Cyrillic) are wider than `0.62em`, so that would trade a safe over-reserve for widespread clipping.
  - A very different font could still over- or under-reserve, but the class shape (narrow < normal < wide) is font-robust. Exact per-glyph widths would need a loaded font (`fontMetrics`), unavailable on this path.
- Above the `20em` clamp the reserve is smaller than the marker needs, so a pathological marker (a very long OCR formula/label) can overlap the content. Proper degradation (switching the absolute-positioned marker to inline) is out of scope here.
- Marker padding is attributed **per nesting level**, so neither item order nor how a list is written on the line can skew a nested list.

  - *One shared registry*, seeded in `ListOpen` and threaded into `ListItems`/`processListChildToken`, so all three written forms attribute the same: the block loop (own-line nested), the same-line form (nested `\begin` in an item body), and the fully single-line / in-cell form.
  - *Resolution* is a single top-down pass (`resolveListPadding`) once the environment is parsed, including on `ListOpen`'s single-line early-return.
  - *Emission rule*: the `2.5em` CSS default is kept on every list; a custom `padding-inline-start` is emitted **only when the widest marker overflows** what the ancestors' indent plus that default already give (`need > sumAncestorP + 2.5em`), reserving just the shortfall (`need − sumAncestorP`). The marker hangs left into the ancestor indent, so nested markers don't compound.
  - *Clamp*: the reserved part (ancestor sum + own shortfall) is capped at `LIST_MAX_INDENT_EM = 20em`; the per-level `2.5em` default still adds on top per level, so a nested pathological marker falls back to the default rather than reserving its full width.
  - *Effects*: flat lists unchanged (`[11.33]` → `3.51em`); ordinary nested lists stay at the default; only a genuinely wide nested marker emits, and less than its full width (`[XXXXXXXXXXXX]` one level deep → `8.93em`, not `11.43em`).
  - *Registry pop* is guarded differently per path: the block loop compares the token itself, the inline path only its kind, because a `*_list_close` carries no link to its opener in the inline stream. An unpaired close of the *same* kind can therefore pop an outer list and leave a later marker unattributed — malformed input only, degrading to the default indent.
  - *Inline-opened lists* never register themselves, but `processListChildToken` walks their token and does. The shapes reaching that path (a sublist after a tabular / fenced-code / figure item, and one inside a tabular cell) are pinned in `tests/_list-marker-padding.js` against the Arial invariant.
  - *Caveat*: the shortfall assumes ancestors render at their `2.5em` CSS default, so a consumer overriding the list CSS could let a very wide nested marker overflow — the emitted value is not self-contained the way a full-width reserve would be. Reproducing `article`'s exact per-depth margins (`\leftmargini..iv`, right-aligned hanging labels) is out of scope here.
- An item with **no inline text immediately followed by a sublist**, where the sublist's marker is wider than the gutter (e.g. `\item[1.]` then a sublist with `\item[3.1.1.1]`), renders with the parent and child markers on the same line, and they can overlap. This **reproduces LaTeX** — `article` in Overleaf overlaps the labels identically (the parent has no text to push the sublist to its own line, and the wide child label hangs into the parent's gutter). It is faithful output for a degenerate construct, not a rendering defect, so it is intentionally not "fixed".
- Image markers (`\item[\includegraphics{…}]`) are reserved by their **alt text**, not the rendered image width — the width model measures text/glyphs, and the image's intrinsic size isn't known on this path.

## Testing

Rendered-HTML behaviour is locked by full-HTML fixtures (input → exact HTML), so a visual regression fails the fixture:

- `tests/_data/_lists/_data.js`: marker padding (per glyph class, math, bold, code-span/html-tag, clamp, mixed, astral, block-content items, fullwidth `11．`), B2 nesting (all written forms, order-independence, sibling sublists, cumulative clamp), empty-`<>` cases, `\item` detection (`\itemsep`/`\itemindent` not mistaken for `\item`), and footnote-terminator cases.
- `tests/_data/_captions/_data.js`: caption numbering (figure/table `1`/`2`/`3`, `\ref`) not shifted by a speculative list parse.
- `tests/_data/_footnotes_latex/_data-footnotetext.js`: a `\footnotetext` whose body contains the word "item"/"items"/"itemize" still renders the footnote.

Non-renderable checks stay as targeted assertions:

- `tests/_list-marker-padding.js`: math `widthEx` per config, no `env` leak from a tabular item, the Arial glyph-width invariant (reserve ≥ true width + gap), the default-indent threshold (narrow glyphs on both sides of it), that only a bare `Nem` reaches the inline style, and a `resolveListPadding` unit test (malformed depth doesn't throw).
- `tests/_display-width.js`: unit tests for `isWideChar`, `textReserveEm`, `tokenMarkerWidth`.
- `tests/_footnotes_latex.js`: a scaling test asserting repeated list + `\footnotetext` units parse linearly (rejects the O(N²) scan).
- `tests/_parse-isolation.js`: a silent `Lists` probe leaves `env` unchanged (full key+value snapshot), for a plain list and for bodies holding a figure / an unclosed table — the cases that exercise `LIST_SPECULATIVE_ENV_KEYS`. Plus the memo-key invariant: a cached probe answer must equal an unmemoized one after mutating each field the key omits (`env.isBlock`, `env.parentType`, `env.prentLevel`, `state.types`, `state.level`), so the day one of them starts affecting the answer the test fails instead of the memo going stale silently.
- `tests/_styles.js`: the `listsStyles` snapshot, plus a tripwire that there is no bare `ul`/`ol` selector.
- Full suite green.
